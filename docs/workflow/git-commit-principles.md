# コミット分割の原則

コミット分割の考え方と判断基準、および履歴を書き換えるときの安全手順。
未コミットの変更を分けるときも、コミット済みの履歴を組み直すときも、このファイルに従う。
「コミット分けて」「履歴整理して」と頼まれたエージェントは、このファイルを読んでから作業する。

粒度とメッセージの必須ルールは [AGENTS.md の「コミット」節](../../AGENTS.md#コミット) にある。
ここではその前提となる考え方と、AGENTS.md に書き切れない判断基準・手順を扱う。

## 粒度の原則

### 1 コミット = 1 つの論理的変更

- **論理的変更**とは、レビュアーが 1 つのまとまりとして理解できる単位
- 複数ファイルにまたがってもよい。逆に 1 ファイル内でも関心事が違えば分ける
- 判断基準: 「このコミットを revert したとき何が失われるか」を一文で言えるか

このリポジトリでは、具体的に「1 コンポーネント / 1 論点」を単位とする
（新規コンポーネントの 3 点セットなどは AGENTS.md を参照）。

### ビルドが通る単位で切る

- 各コミットの時点で **`npx tsc --noEmit` が通ること**は必須（AGENTS.md）
- 理想は、各コミットを単独でチェックアウトしても CI のジョブ
  （`typecheck` / `format:check` / `lint` / `build` / `test:storybook`）がすべて通ること
- 理由: `git bisect` で壊れたコミットを特定できるようにするため
- やむを得ず途中のコミットが壊れる場合は、そのことをコミットメッセージの本文に書く

### 小さすぎても分けない

- typo 修正 1 件だけを独立コミットにするのは分けすぎ
- 関連する小さな修正はまとめる。目安は **diff 全体を 30 秒で把握できる**こと

## 分類の原則

### 生成物と手書きを分ける

- 生成物は手書きのコードと別のコミットにする。
  例: shadcn CLI が生成したコンポーネント
- **例外: `package-lock.json` は `package.json` と同じコミットにする。**
  両者が食い違うと `npm ci` がエラーで止まり、CI の全ジョブが `npm ci` から始まるため、
  そのコミット単独では検証できなくなる
- レビュアーは生成物のコミットを読み飛ばせる
- 生成物だけを差し替えたいとき、手書き部分を巻き込まずに済む

### デザインファイルとコードを分ける

- `design/v3/ui.pen` の変更は、実装のコミットに混ぜず単独のコミット（`design` プレフィックス）にする
- ui.pen は差分をレビューで読めない。実装コミットに混ざると、実装の diff だけを見て判断できなくなる

### リファクタと機能追加を混ぜない

- 機能追加の前にリファクタが必要なら、先にリファクタのコミットを作る
- 「ついでに整理した」はしない。レビューの負荷が一気に上がる
- **見た目と振る舞いが変わらない**ものをリファクタとする。
  Storybook の表示やテスト結果が変わるなら、それはリファクタではない

### テストと実装

| 選択                                 | 履歴                 | CI                   | 使う場面                                     |
| ------------------------------------ | -------------------- | -------------------- | -------------------------------------------- |
| **テストと実装を 1 コミット**（既定）| 失敗状態が残らない   | 全コミットで通る     | 通常                                         |
| **テストを先の独立コミット**         | 失敗の意図が残る     | そのコミットは落ちる | テスト自体がレビュー対象、テスト量が多い     |

- `.stories.tsx` はコンポーネントと同じコミットに置く（AGENTS.md）
- 後者を選ぶ場合は、**そのコミットでテストが落ちることを本文に書く**（`bisect` で混乱しないように）
- バグ修正では後者が有効。「再現するテストを追加する」→「修正する」の 2 コミットにすると、
  レビュアーが diff だけでバグの内容を理解できる

## 順序の原則

### 依存の下から上へ

このリポジトリでの典型的な順序:

1. **ツール・設定**（`package.json`、ESLint / Prettier 設定、`.github/workflows/`）
2. **デザイントークン**（`src/app/_styles/tokens.css`、`src/app/_styles/globals.css`）
3. **外部サービス連携**（`src/infra/` — microCMS のクライアント・型）
4. **共通コンポーネント**（`src/commons/`）
5. **機能コンポーネント**（`src/features/`）
6. **ルーティングの結線**（`src/app/` 配下の `page.tsx` など）
7. **ドキュメント**（`AGENTS.md`、`README.md`、`docs/`、`.agents/skills/`）

各コミットが、それより前のコミットだけに依存するように並べる。
上のコンポーネントを先にコミットすると、そのコミット単独では import 先が無く型が付かない。

### バグ修正は先に切り出す

- 機能追加の途中でバグを見つけたら、**先に**修正コミットを作る
- 理由: 他のブランチへ cherry-pick しやすい。修正だけを先に別 PR に出すこともできる

### ドキュメントは最後

- コードが確定してから書く
- 先に書くと、実装の途中で食い違い、更新を忘れる

## メッセージの原則

### WHY を書く

- 何を変えたかは diff を見れば分かる。本文には**なぜ必要か**を書く
- 「〜の不具合を防ぐため」「〜を巻き添えにしないため」「〜で使えるようにするため」
- 推測で埋めた箇所・自分で決めたロジックは必ず書く（AGENTS.md）

### 件名の書式

このリポジトリの流儀（`git log --oneline` で確認できる）:

- `<種別> <件名>` の形。種別の後ろは**コロンを付けず半角スペース**
- 種別: `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `style` / `design` / `ci`
- 件名は日本語。「〜しました」「〜します」は使わない
- 例:
  - `feat GlobalNav を nav 要素にし label prop を追加`
  - `fix PageNumNav の basePath を必須 prop にして空 href を防ぐ`
  - `refactor ArticlePage のページング計算を articleListPagination に切り出す`

Issue との紐づけは PR 本文の「## 関連 Issue」節で行うため、件名に Issue 番号は入れない。

## アンチパターン

- ❌ `git add -A && git commit -m "update"` — 何が入ったか分からない
- ❌ 「WIP」「fixes」「tmp」コミット — PR を出す前に整理する
- ❌ `--amend` を何度も重ねる — 最初から分け方を決めてから作業する
- ❌ 生成物と手書きを同じコミットにする — 生成物だけ差し替えたいときに困る
- ❌ `ui.pen` の変更を実装コミットに混ぜる — 実装の diff だけで判断できなくなる
- ❌ `src/app/` の結線を、結線先のコンポーネントより前にコミットする — そのコミット単独で型が付かない
- ❌ 並行セッションの未コミット変更を巻き込む — 作業はワークツリーで行い、`git status` で自分の変更だけか確かめる
- ❌ リファクタ・バグ修正・機能追加が入った巨大コミット — 後から分けられない

## 操作の安全手順（履歴を書き換えるとき）

### 1. 中断条件（最初に確認する）

- **`dev` / `desgin-renewal` などの共有ブランチ上にいたら履歴を書き換えない。**報告して止まる
- **未コミットの変更があれば先にコミットする**（stash より確実）
- 次の操作は使わない。取り返しがつかないか、対話入力が必要なため
  - `git reset --hard` / `git clean -f` / `git branch -D`
  - `git rebase -i` / `git add -p`（対話入力ができない）
  - `git push --force` / `--force-with-lease`（ユーザーが明示的に指示した場合のみ。AGENTS.md）

### 2. バックアップを必ず先に作る

```bash
git branch backup/$(git branch --show-current)-$(git rev-parse --short HEAD)
```

**バックアップを作る前に、履歴を書き換える操作は一切行わない。**
復旧は `git switch <バックアップブランチ>` で行う。

### 3. 組み直しは `reset --soft` + unstage + ファイル単位の add

```bash
git fetch origin
base=$(gh pr view --json baseRefName --jq .baseRefName)   # PR の宛先。PR が無ければ宛先ブランチ名を直接書く
git reset --soft $(git merge-base HEAD origin/$base)      # 宛先との分岐点まで戻す
git restore --staged .    # reset --soft は変更を index に残すので、一度すべて unstage する
git add <path>            # ファイル単位。git add -A / git add . は使わない
git commit
```

- **戻す先は PR の実際の宛先ブランチにする。**宛先は `desgin-renewal` とは限らない（`dev` 宛ての PR もある）。
  別のブランチとの分岐点まで戻すと、宛先側にある既存のコミットまで組み直しに取り込んでしまう
- **`reset --soft` の直後に unstage する。**`--soft` は HEAD しか戻さないため、
  そのまま `git add <path>` しても最初の `git commit` にすべての変更が入る
- **`git add -A` / `git add .` を使わない。**無関係なファイルが黙って混入する
- 1 ファイルの中をハンク単位で分ける必要がある場合は、どのハンクをどのコミットに入れるかを
  先にユーザーに示して合意を取る

### 4. 内容が失われていないことを検証する

```bash
git diff backup/<name> HEAD    # 差分なしであること
```

**差分が出たら中断して調べる。**内容が失われている。
あわせて、各コミットで `npx tsc --noEmit` が通ることを確かめる。

### 5. push はユーザーに委ねる

- 新しいコミットを足しただけなら、通常の `git push` でよい
- push 済みのブランチの履歴を書き換えた場合だけ force push が必要になる。
  自分では実行せず、コマンドを提示してユーザーの判断を仰ぐ

```bash
git push --force-with-lease
```

- 作業が終わったらバックアップブランチを消してよいか、ユーザーに確認する
